MDM Training with Auto-Recovery Flow
=====================================

BEFORE FIX (Broken):
--------------------
Training → Loss OK → Loss OK → EXPLOSION! → Load Checkpoint
                                              ↓
                                         Reset Optimizer (same LR)
                                              ↓
                                         Continue Training
                                              ↓
                                         EXPLOSION AGAIN! (same problem)
                                              ↓
                                         Max recoveries reached → FAIL


AFTER FIX (Working):
-------------------
Training → Loss OK → Loss OK → EXPLOSION! → Load Checkpoint
                                              ↓
                                         Reduce LR (e.g., 5e-3 → 2.5e-3)
                                              ↓
                                         Reset Optimizer (with new lower LR)
                                              ↓
                                         Reshuffle Training Data (new batch order)
                                              ↓
                                         Continue Training
                                              ↓
                                         Loss OK! (more conservative + different data order)
                                              ↓
                                         Training succeeds ✓


Detailed Recovery Process:
--------------------------

Step 1: Detection
    Monitor loss after each batch
    ↓
    Loss > threshold OR NaN/Inf?
    ↓
    Yes → Increment bad_steps counter
    ↓
    bad_steps >= patience?
    ↓
    Yes → TRIGGER RECOVERY

Step 2: Recovery
    Find best checkpoint (by val/acc_token)
    ↓
    Load model weights from checkpoint
    ↓
    Calculate new LR:
      new_lr = original_lr × (reduction_factor ^ recovery_count)
      Example: 5e-3 × (0.5 ^ 1) = 2.5e-3
    ↓
    Create fresh optimizer with new LR
    ↓
    Replace trainer's optimizer
    ↓
    Reshuffle training data:
      - If curriculum learning: recreate filtered dataloader with new random order
      - If regular training: reset dataloader to trigger reshuffle
      - Ensures different batch order to avoid repeating problematic sequence
    ↓
    Reset counters: bad_steps = 0
    ↓
    Continue training from current step

Step 3: Prevention
    New lower LR → Smaller gradient updates
    ↓
    Less likely to enter unstable regions
    ↓
    If explosion happens again:
      - Recovery count += 1
      - LR reduced further (e.g., 2.5e-3 → 1.25e-3)
      - Process repeats
    ↓
    After 3 recoveries → Stop training
    (likely a fundamental problem with hyperparameters)


Learning Rate Progression Example:
----------------------------------

Initial:         LR = 5e-3
First recovery:  LR = 2.5e-3  (× 0.5)
Second recovery: LR = 1.25e-3 (× 0.25)
Third recovery:  LR = 0.625e-3 (× 0.125)
Then: Training stops (max_recoveries = 3)


Why This Works:
---------------

1. Checkpoint Loading:
   - Restores model to last known good state
   - Prevents corrupted parameters from propagating

2. Learning Rate Reduction:
   - Smaller steps → more stable optimization
   - Prevents re-explosion in same unstable region
   - Standard practice in LR scheduling

3. Optimizer Reset:
   - Clears momentum/Adam state that might be corrupted
   - Fresh start with new LR
   - Ensures optimizer is aligned with new LR

4. Data Reshuffling:
   - Changes batch order to avoid repeating problematic sequence
   - Prevents model from seeing same "bad batch" that caused explosion
   - Works with curriculum learning (reshuffles within current bin)
   - Adds randomness to break out of unstable patterns

5. Exponential Reduction:
   - Each recovery makes training more conservative
   - Balance between recovery and progress
   - Eventually stops if problem is fundamental


Configuration:
--------------

configs/callbacks/auto_recovery.yaml:
  loss_threshold: 5.0          # Trigger when loss > 5.0
  patience: 3                  # Wait 3 bad steps before recovering
  lr_reduction_factor: 0.5     # Reduce LR by 50% each time
  reset_optimizer: true        # Reset optimizer state (recommended)
  reshuffle_data: true         # Reshuffle training data after recovery
  max_recoveries: 3            # Maximum recovery attempts

Tuning Tips:
  - Lower threshold → more sensitive to instability
  - Higher patience → more tolerance before recovery
  - Smaller reduction_factor → more aggressive LR reduction
  - More max_recoveries → more attempts before giving up
